| K1 | Production MongoDB is a **single self-hosted node** (no failover, no point-in-time restore) shared by the existing system and the new one; plus the known MongoDB 8.0 vs Linux kernel ≥ 6.19 issue (kernel pinned to 6.14) | M | H | Existing daily backup + hourly dump of new collections (RPO ≤ 1 h for new data) + monthly restore test; reconciler + PayU reconciliation after restore; uptime monitoring; kernel stays pinned; HA after launch (DEF-021) |
| K2 | Double booking via race | L | H | `05-…` rules, race test suite, invariant checker in production |
| K3 | Hotels sell same rooms elsewhere | H | H | Allotment contracts, stop-sell, "cannot honour" flow, channel manager in Phase C |
| K4 | Thin inventory at launch | H | H | Start hotel contracting from Stage 03; bedbank adapter early in the roadmap (Stage 17) or earlier if needed |

| K6 | New system breaks or slows something that works today | L | H | `12-protecting-the-existing-system.md`: isolated folder + flag + guarded load, own Mongoose instance, new collections only, read-only legacy access, no server changes, protected-paths CI, pool caps/timeouts, kill switches, rehearsal on a restored production copy with before/after checksums |
| K7 | Wallet/ledger drift | M | H | Ledger invariants, daily reconciliation with PayU |

| K13 | PayU payment succeeds after rooms were lost, or stays pending | L | M | Payment window < hold, one extension, poller, automatic idempotent refunds, clear customer message |

## 3. Questions for a CA and a lawyer (plain language)
